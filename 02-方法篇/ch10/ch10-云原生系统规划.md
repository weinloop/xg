# 第10章 云原生系统规划

> 云原生是面向"云"设计的应用架构体系，通过剥离非业务代码让云设施接管非功能特性，使组织获得弹性、敏捷、安全的全新生产力。

---

## 10.1 云原生发展背景

### 10.1.1 概念

**云原生（Cloud Native）**：拆开看——Cloud 指应用软件和服务在云端而非传统数据中心；Native 代表应用从一开始就基于云环境、专门为云端特性而设计，可充分利用和发挥云计算的弹性与分布式优势。

**发展时间线**：

| 年份 | 事件 | 核心内容 |
|------|------|----------|
| 2010 | Paul Fremantle 博客首次提及 | 分布式、松散、自服务、持续部署与测试 |
| 2013 | Matt Stine 推广 | 推特上迅速传播 |
| 2015 | 《迁移到云原生架构》出版 | 定义12要素、微服务、自服务、基于API协作、抗脆弱性 |
| 2015 | CNCF基金会成立 | Google/Cisco/Docker加入；定位三方面：应用容器化、微服务架构、容器编排调度 |
| 2017 | Pivotal官网概括 | DevOps、持续交付、微服务、容器四大特征 |
| 2018 | CNCF官方定义 | ①容器+服务网格+微服务+不可变基础设施+声明式API ②自动化技术构建高容错松耦合系统 ③统一开源云技术生态 |

**12要素（12-Factor）速查表**：

| 编号 | 要素 | 简介 |
|------|------|------|
| 1 | 基准代码 | 一份基准代码，多份部署 |
| 2 | 依赖 | 显式声明依赖关系 |
| 3 | 配置 | 在环境中存储配置 |
| 4 | 后端服务 | 把后端服务当作附加资源 |
| 5 | 构建、发布、运行 | 严格分离三者 |
| 6 | 进程 | 以一个或多个无状态进程运行应用 |
| 7 | 端口绑定 | 通过端口绑定提供服务 |
| 8 | 并发 | 通过进程模型进行扩展 |
| 9 | 易处理 | 快速启动和优雅终止 |
| 10 | 环境等价 | 保持开发/预发布/线上环境相同 |
| 11 | 日志 | 把日志当作事件流 |
| 12 | 管理进程 | 后台管理当作一次性进程运行 |

**速记口诀：基准依赖配后端，构建进程端口绑，并发易处环境等，日志管理十二全。**

### 10.1.2 发展概述

**一、从烟筒模式到云原生**

传统IT"烟筒"模式→每个应用独立构建、资源难以共享。上云后IaaS层大幅复用，进而推动上层系统统一化，降低建设与运营成本。

**二、开发模式演进**

```
瀑布式流程 → 敏捷开发 → DevOps → DevSecOps
（开发/运维分离）（只解决效率问题）（打通开发运维）（安全融入全流程）
```

- **DevOps**：开发、技术运营和质量保障三者的交集，促进沟通协作整合
- **DevSecOps**：DevOps概念的延续，融合开发、安全及运营理念，在业务应用全生命周期每个环节都为安全负责，是全员（开发+测试+运维+安全）的责任

**三、云原生与新兴场景融合的五个价值体现**：

1. **多元算力支持** — 满足不同场景个性化算力需求，容器/裸机/虚拟机/函数统一计算资源
2. **DevSecOps敏捷开发** — 提升迭代速度，保证全流程安全；侵入和非侵入两种模式
3. **数据资产化** — 快速构建数据运营能力，结合AI实现业务智能升级
4. **数据分析与洞察** — 云原生Operator提供数据分析、商业智能、数据安全保障
5. **全方位安全** — 云平台组织级安全服务和合规能力，云原生数据库弹性伸缩/高可用/自动备份

**速记口诀：算力安全数据，敏捷洞察五价值。**

## 10.2 云原生技术架构

### 10.2.1 架构定义

**云原生架构定义**：基于云原生技术的一组架构原则和设计模式的集合，旨在将云应用中的非业务代码部分最大化剥离，让云设施接管非功能特性（弹性、韧性、安全、可观测性、灰度等）。

**云原生代码三部分**：

| 部分 | 内容 | 地位 |
|------|------|------|
| 业务代码 | 实现业务逻辑的代码 | **核心**，真正带来价值 |
| 三方软件 | 业务代码依赖的三方库（业务库+基础库） | 附属 |
| 处理非功能特性的代码 | 高可用、安全、可观测性等实现代码 | 附属 |

**架构带来的三大变化**：

1. **代码结构巨大变化** — 云把"如何获取存储"变成服务，开发人员不再需要掌握分布式处理技术，业务开发更敏捷快速
2. **非功能性特性大量委托** — 任何应用有功能性特性（业务价值）和非功能性特性（高可用/容灾/安全/可运维性等），云计算在多个层面提供非功能性能力：
   - 虚拟机：检测硬件异常自动热迁移
   - 容器：监控进程异常自动下线/上线/流量切换
   - 云服务：应用变成更薄的"无状态"应用
3. **高度自动化的软件交付** — 容器以标准方式打包软件，IaC/GitOps/OAM/Operator等工具让自动化工具理解交付目标和环境差异

**速记口诀：业务代码是核心，三方非功两附属；代码结构非功委，高度自动三变化。**

### 10.2.2 设计原则

云原生架构七大设计原则：

| 原则 | 核心思想 | 关键要点 |
|------|----------|----------|
| **1. 服务化** | 拆分不同生命周期的业务单元独立迭代 | 面向接口编程、服务流量策略控制（限流降级、熔断隔仓、灰度、反压） |
| **2. 弹性** | 部署规模随业务量自动伸缩 | 不需事先容量规划、缩短采购到上线周期、应对海量突发扩张 |
| **3. 可观测** | 主动通过日志/链路跟踪/度量掌握软件运行 | Logging+Tracing+Metrics、一次点击背后所有调用清晰可见、下钻到SQL/拓扑/网络 |
| **4. 韧性** | 软件抵御各类异常的能力 | 提升MTBF、异步化/重试/限流/降级/熔断/反压、主从/集群/AZ高可用/异地多活 |
| **5. 所有过程自动化** | IaC/GitOps/OAM/Operator等工具标准化+自动化交付 | CI/CD流水线、面向终态交付、配置数据自描述 |
| **6. 零信任** | 默认不信任任何人/设备/系统 | 从"网络中心化"走向"身份中心化"、基于认证和授权重构信任基础 |
| **7. 架构持续演进** | 架构是动态快照，非静态等式 | 增量迭代、架构治理和风险控制、存量迁移考虑迁出成本和迁入成本 |

**速记口诀：服务弹性可观测，韧性自动零演进。**

### 10.2.3 架构模式

云原生七大架构模式：

| 模式 | 核心思想 | 要点 |
|------|----------|------|
| **1. 服务化架构** | 以接口契约定义业务关系，标准协议互联互通 | 微服务/小服务模式、DDD/TDD/容器化、单独扩缩容 |
| **2. Mesh化架构** | 中间件框架从业务进程分离 | Client只负责与Mesh通信、熔断/限流/降级由Mesh进程完成 |
| **3. Serverless** | 将"部署"从运维中收走 | 事件驱动型计算任务、不适用有状态/长后台/频繁I/O应用 |
| **4. 存储计算分离** | 各类暂态/持久数据用云服务保存 | 无状态应用获更好弹性和AP、时间日志+快照增量恢复 |
| **5. 分布式事务** | 微服务私有数据源下的事务处理 | XA（强一致性能差）/消息最终一致/TCC/SAGA/SEATA AT五种模式 |
| **6. 可观测架构** | Logging+Tracing+Metrics三方面 | 定义SLO、OpenTracing/OpenTelemetry框架、spanid/traceid关联 |
| **7. 事件驱动架构** | 应用/组件间基于事件的异步集成 | Event有Schema可校验、用于韧性/CQRS/数据通知/开放接口/事件流/IoT |

**分布式事务五种模式对比**：

| 模式 | 一致性 | 性能 | 开发成本 |
|------|--------|------|----------|
| XA | 强 | 差 | 低 |
| 消息最终一致 | 最终 | 高 | 中 |
| TCC | 可控 | 高 | 高 |
| SAGA | 可控 | 高 | 高 |
| SEATA AT | 高 | 非常高 | 无代码 |

**速记口诀：服务Mesh无服务，存储事务可观测，事件驱动七模全。**

### 10.2.4 架构优势

六大优势：

| 优势 | 说明 |
|------|------|
| **高可扩展性** | 微服务独立部署扩展，快速增减实例 |
| **高可用性** | 多节点负载均衡和容错处理，减少单点故障 |
| **灵活性** | 不同编程语言和技术栈，满足不同场景 |
| **安全性** | 容器化隔离、自动化减少人为错误 |
| **成本效益** | 更高ROI，减少运维成本 |
| **高度自动化** | 与基础设施深度整合，PaaS接管运维 |

**速记口诀：扩展灵活可用性，安全成本自动化。**

## 10.3 云原生建设规划

### 核心原则：顶层规划＋分步实施

云原生架构体系内容众多，不可能一步到位，需要通过一系列项目持续建设。**五步实施路线图**：

| 步骤 | 内容 | 关键工作 |
|------|------|----------|
| **第1步** | 微服务采用及容器云平台构建 | 构建Kubernetes容器云平台；以12要素指导微服务设计（DDD方法/"主数据驱动设计"方法）；Martin Fowler建议先建大统一系统再重构 |
| **第2步** | 服务管理和治理 | 完善服务治理和API定义；Kubernetes之上扩展治理能力；Service Mesh代理东西流量；Spring Cloud框架；区分微服务API和OpenAPI两层 |
| **第3步** | 持续交付及安全 | DevOpS理论指导构建CI/CD闭环；代码/镜像/系统/应用/接口/容器安全检查；建议自研或合作研发避免开源工具集成问题 |
| **第4步** | 自服务敏捷响应基础设施 | 统一身份认证/日志/配置/监控/告警/安全/AI/消息/调度等基础服务；多云管理平台封装异构资源；组织架构同步调整（资源团队/平台团队/工具团队/应用团队） |
| **第5步** | 增强生产环境韧性和安全性 | 抗脆弱性（Antifragility）——主动注入故障找到弱点并强制修复；混沌猴（Chaos Monkey）思想；安全能力持续改进 |

> 💡 **"主数据驱动设计"**：基于组织主数据设计的微服务天然具备系统间可重用性，结合行业通用数据模型（CDM）减少重复迭代。

**速记口诀：容器治理交付安，基础韧性五步全。**

## 10.4 云原生实践案例

### 某快递公司核心业务上云案例

**背景**：
- 日订单处理量千万级，亿级物流轨迹，每天TB级数据，1300+计算节点
- 原有IDC架构（VMware+Oracle数据库）暴露问题：交付周期长、大促资源难保障、系统稳定性差

**三大改造**：

| 改造项 | 具体方案 |
|--------|----------|
| 引入云原生数据库 | OLTP与OLAP分离，改变完全依赖Oracle的局面 |
| 应用容器化 | 解决环境不一致，确保开发/测试/生产一致 |
| 微服务改造 | Kubernetes服务发现，按业务域拆分，摆脱存储过程和触发器的依赖 |

**五层架构**：

| 层次 | 内容 |
|------|------|
| 基础设施 | 裸金属服务器，按需取量，随取随用 |
| 流量接入 | 公网/内网两套；Ingress统一域名转发 |
| 平台层 | Kubernetes PaaS：DevOps闭环、资源隔离、流量精细管理、日志/链路/Metrics集成 |
| 应用服务层 | 每个应用独立Namespace，YAML模板快速部署和回滚 |
| 运维管理 | 托管版容器服务，自动完成扩容 |

**四大应用效益**：
1. **成本** — 随用随付，免运维节省人工成本
2. **稳定性** — 至少5个9（99.999%）SLA，数据异地备份
3. **效率** — CI/CD分钟级，SLS日志控制台快速定位问题
4. **赋能业务** — 300+云上组件开箱即用
