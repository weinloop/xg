## 📖 二、逐节知识精炼

### 5.1 基础知识

**应用系统建设的特点**：行业领域个性化突出、可复用性低、投资大、周期长、复杂度高。科学的应用系统规划 → 减少盲目性、整体性好、适用性高、阶段有序、节约资源。

**三类规划设计覆盖范围**：
| 类型 | 内容 |
|------|------|
| 应用系统整体规划 | 统筹所有应用系统，形成集合及关系，明确内容及发展路径 |
| 应用系统业务条线规划 | 针对业务条线（如业财体系、仓储物流体系）进行体系性定义 |
| 应用软件设计 | 针对具体职能或业务活动域，进行软件模块定义（功能/非功能/模块划分） |

**核心业务逻辑**：基于业务需求，按「需求 → 抽象 → 体系 → 配套」过程实现内容定义。

#### 5.1.1 基本概念（9个）（口诀：抽体模关模信功求重）

> M.A. Jackson：「软件工程师的智慧开始于认识到『使程序工作』和『使程序正确』之间的差异。」这9个概念为「使程序正确」提供了框架。

**1. 抽象**

从众多事物中抽取共同的本质特征。多层级抽象：

| 抽象层级 | 描述语言 | 示例 |
|---------|---------|------|
| 最高抽象级 | 环境语言、概括性术语 | 业务效率提升、计划调度可视化 |
| 较低抽象级 | 详细方案说明 | 审批流定义、信息表单定义、前端界面定义 |
| 最低抽象级 | 可直接实现的方式 | 具体代码/配置 |

**四种抽象类型**：

| 类型 | 定义 | 要点 |
|------|------|------|
| **业务抽象** | 将复杂业务活动转化为可管控、可显性表达、可重用的业务区块 | 聚焦价值本质，忽略低价值活动；本质是面向场景建模 |
| **过程抽象** | 具有明确和有限功能的指令序列 | 暗示功能但隐藏细节（如「开门」隐含一系列步骤） |
| **数据抽象** | 描述数据对象的具体数据集合 | 如「门」的属性：类型、转动方向、开门方法、重量、尺寸 |
| **技术抽象** | 描述问题解决所需可持续开发利用的技术体系 | 关注技术可持续性，确保整体与局部技术一致性 |

**2. 体系架构**

应用系统的组成结构（系统/模块/构件层次）+ 交互方式 + 数据结构。

**架构特性**：内部特性（组成部分封装方式、相互作用方式）+ 外部功能特性（发展/性能/功能/可靠性/安全性/可适应性需求）。

**四种架构模型**（口诀：框动过功）：

| 模型类型 | 作用 |
|---------|------|
| 框架模型 | 通过确定相似应用中的可复用架构框架提高抽象级别 |
| 动态模型 | 强调架构行为方面，指明结构/配置随外部事件的变化 |
| 过程模型 | 强调系统必须提供的业务或技术流程设计 |
| 功能模型 | 表示系统的功能层次结构 |

**3. 模式**

模式是**最佳实践的表达方法**，承载已证实解决方案的精髓。

| 模式类型 | 示例 |
|---------|------|
| 创建型模式 | 工厂模式、原型模式、建造者模式 |
| 结构型模式 | 组合模式、桥接模式、代理模式 |
| 行为型模式 | 责任链模式、状态模式、指令模式 |

每种模式用来回答三个问题：①是否适用于当前工作？②能否复用（节约设计时间）？③能否指导下一个相似模式？

**4. 关注点分离**

将复杂问题分解为可独立解决或优化的若干块，降低认知复杂度。两个问题结合的认知复杂度 > 各自认知复杂度之和 → 「分而治之」策略。

**5. 模块化**

应用系统的单一属性，使其能被智能化管理。将系统划分为独立命名的、可处理的模块（子系统/构件），集成后满足需求。降低构建成本。

**6. 信息隐蔽**

每个模块对其他所有模块隐蔽自己的规划设计决策（算法和数据都包含在模块内）。好处：修改过程中引入的错误不太可能传播到其他地方。

**7. 功能独立**

通过具有专一功能、避免与其他模块过多交集的模块实现。两条定性评估标准：

| 标准 | 含义 | 关系 |
|------|------|------|
| **内聚性** | 模块相关功能的强度（一个内聚模块应只完成一件/一类事情） | ↓ 内聚 ↔ ↑ 独立 |
| **耦合性** | 模块间的相互依赖性（应尽力得到最低耦合） | ↑ 耦合 → 「涟漪效果」 |

> 功能独立是良好规划设计的关键，规划设计又是应用系统质量的关键。

**8. 求精（逐步求精）**

自顶向下策略，通过逐步分解功能的宏观陈述进行层次建设，直至到达编程语言可描述的层级。抽象和求精是互补概念：抽象隐藏低层细节，求精揭示低层细节。

**9. 重构**

重新组织的技术，简化设计而不改变功能或行为。重点检查：冗余性、未使用元素、低效算法、不恰当数据结构等，修改以获得更好的设计。

---

#### 5.1.2 基础架构（4种）（口诀：分数组中）

应用系统体系架构 = 建立在系统支持环境基础上的系统基本框架（骨架）。

**1. 分层体系**

应用系统从上至下四层：

| 层次 | 功能 | 构造元素 |
|------|------|---------|
| **界面交互层** | 实现系统与环境交互 | 界面控件（按钮、文本框等） |
| **业务处理层** | 实现业务流程控制与业务数据计算 | 业务子系统、功能构件 |
| **数据处理层** | 实现数据读写处理 | SQL函数包（视图/存储过程/触发器） |
| **数据存储层** | 实现数据有效存储 | 数据表、数据文件 |

**2. 以数据为中心的架构**

适用于以数据处理、统计、汇总为业务特征的系统。设计路线：先规划设计好数据环境 → 按数据业务应用划分来设计各子系统。

**3. 客户机/服务器架构**

| 架构类型 | 结构 | 优点 | 缺点 |
|---------|------|------|------|
| **两层C/S** | 客户机（界面+业务）→ 数据库服务器 | 结构简单、容易实现、操作性能好 | 管理维护不便、变更成本大 |
| **三层C/S** | 客户机 → 应用服务器（业务）→ 数据库服务器 | 集中更新业务规则，利于维护 | 技术难度大、硬件性能要求高 |
| **B/S架构** | 浏览器 → Web服务器 → 应用服务器 → 数据库 | 无须维护客户机、支持远程信息服务 | 传输速度/安全性/稳定性低于C/S |

**4. 组件分布架构**

通过组件集成软件，建立分布式应用系统体系。组件可部署在多台计算机节点上，相互通信、协同作业。

**三大组件分布中间件**：

| 中间件 | 全称 | 特点 |
|--------|------|------|
| **CORBA** | 通用对象请求代理模型（OMG定义） | 通用性强，UNIX/Linux/Windows广泛支持 |
| **DCOM** | 分布式组件对象模型（微软） | 基于COM，通用性不如CORBA |
| **EJB** | 企业Java Bean（Sun） | 基于Java的分布式组件对象模型 |

### 5.2 主要内容（五大定义）（口诀：生体接数构）

五大定义：**生命周期选择 → 体系结构定义 → 接口定义 → 数据定义 → 构件定义**。

#### 5.2.1 生命周期选择

生命周期模型 = 包含开发、运行、维护中过程活动和任务的框架。需包含：需求识别→开发→测试→安装→运行→退役。

**四种生命周期模型对比**：

| 模型 | 核心特点 | 优点 | 注意事项 |
|------|---------|------|---------|
| **瀑布模型** | 阶段间顺序依赖、推迟实现、每阶段评审 | 质量保证、逻辑/物理设计分离 | 不适应需求变化 |
| **V模型** | 测试活动与分析/设计相关联，编码在顶点 | 验证各阶段正确实现 | 瀑布变种 |
| **迭代模型** | 演化建设或增量建设 | 缩短面世时间、失败风险低、重要部分测试多 | 不破坏已部署系统、架构必须开放 |
| **敏捷方法** | 4核心价值+12原则、个体互动>流程工具 | 快速响应变化、持续交付价值 | 不适用所有项目/产品/人/情况 |

**敏捷宣言4种核心价值**：
1. 个体和互动 **高于** 流程和工具
2. 工作的软件 **高于** 详尽的文档
3. 客户合作 **高于** 合同谈判
4. 响应变化 **高于** 遵循计划

**生命周期模型选择**：每个模型都包含通用活动（需求→规划设计→构造→测试→阶段出入口标准），应根据需求组合选择适合的模型元素。

---

#### 5.2.2 体系结构定义

采用**结构化方法**定义，划分为：

**1. 面向数据流的定义方法**（概要阶段常用）

| 数据流类型 | 特征 | 设计三步骤 |
|-----------|------|-----------|
| **变换型** | 输入→加工变换→输出 | ①区分输入/变换中心/输出 ②得初始结构图 ③优化 |
| **事务型** | 输入→事务中心→选择执行路径 | ①找出事务中心/接收数据/处理路径 ②转初始结构图 ③分解细化分支 |

复杂系统通常同时存在两种数据流。

**2. 面向数据结构的定义方法**（详细设计阶段常用）

根据数据结构设计程序处理过程。Jackson方法同时考虑输入/输出数据结构，三种基本类型：顺序型、选择型、循环型。

**3. 表示工具**

| 工具 | 特点 |
|------|------|
| **层次图（HIPO图）** | 矩形框=模块，连线=调用关系，带编号 |
| **结构图** | 方框=模块，带注释箭头表示传递信息（空心=数据，实心=控制） |

---

#### 5.2.3 接口定义（口诀：用外内）

接口定义 = 功能描述 + 输入/输出定义 + 错误处理。

**三类接口**：

| 接口类型 | 说明 |
|---------|------|
| **用户接口** | 命令及语法结构、系统回答信息 |
| **外部接口** | 系统与外界的所有接口（软件-硬件、系统-支持系统） |
| **内部接口** | 系统内各元素之间的接口 |

**界面设计三大黄金原则**（口诀：控记一）：

| 原则 | 要点 |
|------|------|
| **置用户于控制之下** | 不强迫不必要的动作、灵活交互、可中断撤销、隔离技术细节 |
| **减少用户记忆负担** | 减少短期记忆、有意义的默认值、直觉性捷径、现实世界隐喻 |
| **保持界面一致** | 保持语境、不改变已有交互模式（除非不得已） |

**界面定义需考虑的4个问题**：系统响应时间、用户求助机制、出错信息、命令方式。

---

#### 5.2.4 数据定义

将数据对象转换为数据结构和数据库（程序级 + 应用级）。

**数据库定义5步骤**（口诀：需概逻物验）：
1. **需求分析** → 弄清数据种类/范围/数量，形成用户需求规约
2. **概念模型** → 抽象概念数据模型，避开计算机实现细节
3. **逻辑模型** → 转换为特定DBMS支持的逻辑数据模式
4. **物理数据库** → 选定物理存储结构/存取方法/存取路径
5. **验证** → 运行典型任务验证正确性和合理性

---

#### 5.2.5 构件定义

将需求模型和架构模型转化为构件表示。典型任务：

- 标识所有与问题域对应的类
- 确定所有与基础设施域对应的类（GUI/操作系统/数据管理构件）
- 细化不需复用的类（接口/属性/操作，考虑内聚和耦合）
- 说明持久数据源及管理类
- 细化类/构件的行为表示（UML状态图）
- 细化部署图（构件包位置）
- 迭代重构

---

### 5.3 主要过程（五步法）（口诀：初可详分设）

> ⚠️ **重要**：5个过程构成完整系统建设链路，是案例和论文的高频考点。

**总体链路**：初步调研 → 可行性研究 → 详细调研 → 系统分析 → 系统设计

#### 5.3.1 初步调研

**目标**：掌握用户概况，识别问题和初始需求，明确初步目标，为可行性研究提供基础。

**特点**：高层、宏观、全面，不需要过于具体细致。

**调研5方面内容**（口诀：组环现态资）：
| 内容 | 要点 |
|------|------|
| 组织概况 | 规模、历史、行业、管理目标、人力物力 |
| 组织环境 | 自然环境、社会经济环境、上下级/横向关系 |
| 现行系统概况 | 功能、技术、效率、可靠性、人才、管理体制、问题 |
| 各方面态度 | 迫切性、领导决心、人员积极性 |
| 资源情况 | 现有/可投入的人力、物力、设备、财力、时间、限制条件 |

---

#### 5.3.2 可行性研究

**定义**：项目正式开发前，从经济、技术、管理、社会等方面进行全面系统分析和科学论证。

**三种结论**：①可行，按计划进行 ②基本可行，需修改 ③不可行，不立项或终止。

**四方面分析**（口诀：经技社管）：

| 方面 | 核心问题 | 关注点 |
|------|---------|--------|
| **经济可行性** | 是否值得建设？ | 总成本（建设+运行）vs 总收益（直接效益+间接社会效益） |
| **技术可行性** | 技术资源可用吗？ | 全面考虑所有技术、优选成熟技术、慎重引入先进技术、开发人员能力匹配 |
| **社会可行性** | 与社会环境相符吗？ | 政策/法律/道德/制度/管理/人员 + 操作可行性 |
| **管理可行性** | 领导支持吗？ | 组织领导支持度、管理人员配合度、管理基础、变革接受度 |

**经济可行性 — 成本构成**：①设备成本 ②人员成本 ③材料成本 ④其他成本

**经济可行性三种结论**：①效益 > 成本 ✓ ②成本 > 效益 ✗ ③基本持平（需综合考量间接效益）

**可行性研究8步骤**：
1. 复查系统目标和规模
2. 研究目前正在使用的系统
3. 导出新系统的高层逻辑模型
4. 重新定义问题（前4步构成迭代循环）
5. 导出和评价供选择的方案
6. 推荐一个方案并说明理由
7. 草拟开发计划
8. 书写文档并提交审查

**可行性研究报告主要内容**：建设任务提出 → 系统目标 → 初步调研概况 → 初步实施方案与比较 → 可行性研究 → 结论（三种之一）

**可行性论证会**：报告提交后召开，两种可能结果：①同意/基本同意 ②持不同意见（影响结论则重新调查，不影响则留待详细调研）

---

#### 5.3.3 详细调研

**目标**：完整掌握现行系统现状，查明执行过程，发现问题和薄弱环节，为系统分析做准备。

**与初步调研的区别**：工作量大得多、细致程度高得多、涉及业务/人/数据/信息多。

**6大调研原则**（口诀：自用分工全主）：
1. **自顶向下全面展开** — 从最顶层开始，逐层深入
2. **用户参与** — 业务人员+设计人员共同进行
3. **分析改进可能性** — 保持冷静，先搞清楚现实再分析优化
4. **工程化工作方式** — 事先计划、统一规范、结果归档
5. **全面与重点相结合** — 全面铺开但侧重与目标系统相关的分支
6. **主动沟通和友善工作方式** — 积极沟通、建立良好人际关系

**详细调研9个范围**：
①组织和功能业务 ②组织目标和发展战略 ③工艺流程和产品构成 ④数据和数据流 ⑤业务流程和工作形式 ⑥管理方式和具体方法 ⑦决策方式和过程 ⑧可用资源和限制条件 ⑨现存问题和改进意见

**详细调研5种方法**（口诀：收发开访深）：

| 方法 | 说明 |
|------|------|
| 收集资料 | 收集各部门计划/原始凭证/单据/报表 |
| 发调研表 | 重点询问（列出关键因素编问卷）+ 全面业务需求分析问卷 |
| 开调研会 | 按职能部门或各类人员联合座谈 |
| 访问 | 个别访问，补充调研会不足 |
| 深入实际 | 参加业务实践，收集试验数据 |

#### 5.3.4 系统分析

**任务**：系统分析师与用户一起充分了解需求，用系统说明书表达双方理解。回答新系统「做什么」的问题。

**三个阶段**（口诀：问需定）：

| 阶段 | 核心工作 | 输出 |
|------|---------|------|
| **问题分析** | 需求调研，了解业务，获取原始需求 | 对业务系统的理解、原始需求 |
| **需求分析** | 分析员与用户充分交流，准确完整获取系统需求 | 功能性需求 + 非功能性需求 |
| **需求定义** | 整理并建立最终需求模型，详细定义每项需求 | 需求规格说明 |

**问题分析需明确的4个事项**：
- 建设背景（为什么有这个项目？没有会怎样？）
- 解决的问题/涉及的人、单位/目标/范围/成功标准
- 关键利益相关人员和待解决问题
- 详细调查分析业务流程，建立业务流程模型

**三种需求引导方法**（口诀：原J观）：

| 方法 | 说明 | 优缺点 |
|------|------|--------|
| **原型法** | 快速构造原型，请用户提修改意见 | 直观→深度沟通；缺点：额外工作量成本 |
| **JAD会议** | 联合应用开发，所有利益相关者集中讨论 | 发挥群体智慧；缺点：人员多难控制 |
| **观摩法** | 参观同行业成功系统 | 类比思维获取需求，缩短周期 |

**四种常用需求分析方法**（口诀：结信U敏）：

| 方法 | 特点 | 核心模型 |
|------|------|---------|
| **面向过程的结构化方法** | 自顶向下、逐层分解 | 数据流图 |
| **面向数据的信息工程方法** | 以数据为中心，先分析数据需求 | 实体关系图 |
| **基于UML的用例驱动方法** | 兼顾功能+数据需求，目前最流行 | 用例图 + 领域类图 |
| **基于敏捷的用户故事** | 最轻量级，自然语言描述 | 用户故事 |

**系统说明书六大特征**（口诀：正完一义修跟）：正确性/完整性/一致性/无二义性/可修改性/可跟踪性

**系统说明书三大内容**：引言（项目名称/目标/背景/术语）→ 概述（主要工作/现行系统/功能需求/数据需求/其他需求）→ 实施计划（任务分解/进度/预算）

#### 5.3.5 系统设计

**总体任务**：从系统逻辑模型出发，结合实际条件，设计系统物理模型。解决「如何做」的问题。

**两个阶段**：总体设计（框架概貌）→ 详细设计（具体化、条理化、规范化）

**五大评价指标**：

| 指标 | 含义 | 提高措施 |
|------|------|---------|
| **可靠性** | 抵御干扰的能力及恢复能力 | 立法/硬件/软件/运行环境/规程；冗余/身份验证/防火墙 |
| **可变更性** | 可维护性或可修改性 | 结构化模块设计、数据规范化、功能前瞻性 |
| **效率** | 响应时间或单位时间处理量 | 硬件平台/系统软件/参数/应用结构设计 |
| **通用性** | 不同单位的可应用程度 | 业务处理规范化/标准化/完善化 |
| **工作质量** | 数据准确性/输出易懂性/操作方便性 | 硬件+软件质量、考虑使用者要求 |

**五大设计原则**（记忆口诀：系灵可经管）：
1. **系统性** — 系统是整体，代码统一、规范统一、数出一处
2. **灵活性** — 预见性、开放性、模块化、低耦合
3. **可靠性** — 安全保密性、检错纠错、抗病毒、系统恢复
4. **经济性** — 满足需求前提下减小开销，避免不必要复杂化
5. **管理可接受** — 考虑业务类型/人员素质/界面友好/操作难易

**系统设计10项内容**：
系统总体结构设计 → 处理流程设计 → 代码设计 → 人机界面设计 → 输出设计 → 输入设计 → 数据库设计 → 安全保密设计 → 系统物理配置方案设计 → 编写系统设计说明书

### 5.4 常用方法 ⭐（口诀：组框务）

> 🔥 **五星重要**：APA/TOGAF/SOA是综合选择题的高频考点。口诀「组框务」分别对应 APA 应用系统组合法、TOGAF 开放组架构框架、SOA 面向服务的架构。

#### 5.4.1 APA 应用系统组合法

**目标**：评估和管理组织应用系统，确定保留/更新/替换/淘汰，优化应用系统组合。

**六步过程**（口诀：清评分策实监）：

| 步骤 | 内容 |
|------|------|
| 1. 应用系统清单 | 收集整理系统名称/功能/技术平台/使用情况 |
| 2. 评估应用系统 | 业务价值/技术健康/维护成本/风险评估（问卷/访谈/数据分析） |
| 3. 分析应用系统组合 | 分类分析，识别重复/冗余/过时系统 |
| 4. 制定优化策略 | 更新替换旧系统、整合重复、淘汰不必要 |
| 5. 实施优化计划 | 系统开发/数据迁移/培训等 |
| 6. 监测和评估 | 确保优化效果，根据需要调整改进 |

#### 5.4.2 TOGAF 开放组架构框架

**四大目标**：①统一语言 ②避免锁定专有方案 ③节省时间和金钱 ④实现可观ROI。

**TOGAF 9 六大组件**（口诀：A指内连参能）：

| 组件 | 内容 |
|------|------|
| **ADM（架构开发方法）** | TOGAF核心，开发企业架构的分步方法 |
| **ADM指南和技术** | 应用ADM的指南和技术集合 |
| **内容框架** | 结构化元模型、可重用构件块、典型可交付成果 |
| **企业连续体和工具** | 分类法和工具，分类存储架构活动输出 |
| **TOGAF参考模型** | 技术参考模型 + 集成信息基础设施参考模型 |
| **架构能力框架** | 建立和运营架构实践所需的组织/流程/技能/角色/职责 |

**ADM 全生命周期10阶段**：

| 阶段 | 活动 |
|------|------|
| 预备阶段 | 准备：定义组织/架构框架/原则/工具 |
| 需求管理 | 需求识别/保管/交付，贯穿全过程 |
| A. 架构愿景 | 设定范围/约束/期望，创建架构工作说明书 |
| B. 业务架构 | 开发基线/目标架构描述，执行差距分析 |
| C. 信息系统架构 | 应用架构 + 数据架构 |
| D. 技术架构 | 技术层面架构开发 |
| E. 机会和解决方案 | 初步实施规划，确定构建块交付形式 |
| F. 迁移规划 | 绩效/风险分析，制定详细实施和迁移计划 |
| G. 实施治理 | 定义架构限制，提供架构监督，监测实施 |
| H. 架构变更治理 | 持续监测和变更管理，最大化架构价值 |

**ADM 三级迭代**：①架构开发整体迭代 ②多个开发阶段间迭代 ③一个阶段内部迭代

#### 5.4.3 SOA 面向服务的架构

**定义**：将应用程序的不同功能单元通过定义良好的接口和契约联系起来，独立于硬件平台/操作系统/编程语言。

**六大设计原则**：
1. **明确的接口定义** — 稳定、明确、封装
2. **自包含与模块化** — 完全独立自主、独立部署/版本控制/自我管理
3. **粗粒度** — 服务数量不应太多，消息交互而非RPC
4. **松耦合** — 减少依赖，位置/技术/状态对请求者不可见
5. **互操作性、兼容性和策略声明**

**六大技术内容**：

| 技术 | 内容 |
|------|------|
| **服务封装** | 将业务功能封装成标准化服务 |
| **服务编排** | 多个服务组合成复杂业务流 |
| **服务注册与发现** | 注册中心存储服务信息，查询找到所需服务 |
| **服务治理** | 生命周期管理/质量保障/服务间协同（注册/授权/监控/日志/告警） |
| **服务安全** | 身份认证/访问控制/数据加密 |
| **服务可靠性和可用性** | 通过合理设计和部署提高 |

**五大应用场景**（口诀：集流扩云跨）：组织级应用集成 → 业务流程管理 → 系统扩展和重用 → 云计算和微服务 → 跨平台集成

### 5.5 软件工厂

**核心理念**：将软件开发视为工业化生产过程，类似传统制造业生产线。模板一次编写，生成多样化产品。

**五大构成**：

| 构成 | 内容 |
|------|------|
| **专业人员** | 开发/测试工程师、项目经理、产品主管 |
| **基础设施和硬件** | 终端计算机、服务器、网络设备 |
| **工具和技术** | 项目管理工具、IDE、自动化测试、版本控制、编程语言、数据库 |
| **流程规范和方法论** | DevSecOps、CI/CD等 |
| **质量管理** | 软件测试、代码审查、性能测试 |

**发展历程**：1955年兰德公司提出 → 1970s Royce完善 → 1990s工业化自动化 → 2000s敏捷开发 → 2010s DevOps/CI/CD → 现在AI/ML驱动

**4. 协同开发**
- 团队协作和沟通（站会/评审会/回顾会）
- 共享知识和经验（文档知识库/代码审查/技术分享会）

**实施步骤**：确定需求和目标 → 选取软件解决方案 → 系统定制开发 → 测试验证 → 部署培训 → 监控维护

**4. 体系保障**

| 文档和记录体系 | 需求规格/设计文档/测试报告/用户文档 |

**5.5.4 应用场景**：①软件开发组织（嵌入式/桌面/Web/移动应用） ②软件项目交付（发布管理/安全检查/事件响应 + 运营：安全监控/安全运营/风险评估/应急响应/升级变更/服务支持/运营反馈）

### 首考已验证

### 易混淆点

| 易混淆 | 区分 |
|--------|------|
| 抽象 vs 求精 | 抽象=隐藏低层细节向上层提供简化视图；求精=自顶向下逐步揭示低层细节 |
| 内聚性 vs 耦合性 | 内聚=模块内部功能强度（越高越好）；耦合=模块间依赖程度（越低越好） |
| 变换流 vs 事务流 | 变换流=输入→加工→输出；事务流=输入→事务中心→选择执行路径 |
| 两层C/S vs 三层C/S | 两层=客户机含界面+业务；三层=业务提取到独立应用服务器 |
| 原型法 vs JAD会议 | 原型法=快速造原型→用户反馈；JAD=所有人集中开会讨论 |
| 系统分析 vs 系统设计 | 分析回答「做什么」（逻辑模型）；设计回答「如何做」（物理模型） |
| APA vs TOGAF vs SOA | APA=评估优化现有组合；TOGAF=标准化企业架构开发方法；SOA=服务化的架构设计模型 |
| ADM 10阶段 | A=愿景 B=业务 C=信息系统 D=技术 E=机会方案 F=迁移 G=实施治理 H=变更治理（+预备+需求管理） |
