## 一、研发管理工具

### 1.1 软件开发工具（IDE）

软件开发工具是辅助软件开发、运行、维护、管理和支持等活动的应用系统，目的是**降低开发和维护成本、提高生产效率、改进产品质量**。

**两个层次**：
- **孤立工具**：单个工具，不同界面、不同数据格式，彼此独立
- **集成化CASE环境**：多阶段工具集成，一致界面，共享信息数据库

| 工具 | 核心定位 | 关键特性 | 适用场景 |
|------|---------|---------|---------|
| **Visual Studio** | 微软全栈IDE | 多语言/多平台、VSTS协作、强大调试 | .NET/Web/移动开发 |
| **Eclipse** | 开源可扩展平台 | 完全开源、跨平台、插件化(PDE) | Java开发为主 |
| **PyCharm** | Python专业IDE | 智能代码编辑、远程开发、数据库工具 | Python/数据科学 |

### 🔥 华航实战：为什么用了VS又用PyCharm？

> 平台后端API服务使用.NET Core开发（团队主力技术栈），选择**Visual Studio 2022**作为主力IDE，利用其强大的调试编译功能和VSTS（Azure DevOps）做敏捷管理。数据引擎和AI模块用Python开发，团队使用**PyCharm Professional**，利用其远程开发功能直接连接到开发服务器的Docker环境调试。两个IDE通过统一的GitLab代码仓库协作。

### 1.2 代码管理工具

代码管理工具用于存储、追踪代码和目录及其修改历史，主要分两类：

| 特性 | **SVN（集中式）** | **Git（分布式）** |
|------|-----------------|-----------------|
| 架构 | C/S模式，中央服务器 | 本地+远程仓库 |
| 离线工作 | ❌ 必须连接服务器 | ✅ 完整本地仓库 |
| 分支操作 | 慢，需服务器通信 | 快，纯本地操作 |
| 安全性 | 服务器故障即数据丢失 | 任意副本可恢复 |
| 版本标识 | 递增版本号 | SHA-1哈希 |
| 典型场景 | 小型团队、强管控 | 大规模分布式团队 |

### 🔥 华航实战：为什么要Git不要SVN？

> 项目29节点分布在3个城市，团队也跨地域协作。SVN的集中式架构意味着任何节点的网络波动都会阻塞开发流程。我们选择**GitLab自建私有仓库**，每个开发人员拥有完整代码库，即使离线也能提交、查看日志、创建分支。Git的分支模型（feature分支→develop→master）天然适合7个模块并行开发。代码审查通过GitLab MR（Merge Request）机制强制进行。

### 1.3 软件配置管理工具 — 8大功能

软件配置管理（SCM）是贯穿软件开发始终的重要质量保证活动。

::: tip 核心口诀
**「项版增程资自期集」**
:::

| 序号 | 功能 | 说明 |
|:---:|------|------|
| 1 | **项**目管理 | 建立配置管理计划、创建配置库，确定配置项范围 |
| 2 | **版**本管理和基线控制 | 记录修改轨迹，基线渐进方式推进开发 |
| 3 | **增**强的版本控制 | 快照（多文件版本集合）+ 分支并行开发 |
| 4 | 流**程**控制和变更管理 | 问题跟踪 + 变更请求管理 |
| 5 | **资**源维护 | 沙箱技术为并行开发提供独立工作空间 |
| 6 | 过程**自**动化 | 事件触发机制（如"增加成员"自动触发"填功能描述表"） |
| 7 | 管理整个生命周**期** | 从开发→测试→发布→维护，预置模板+支持自定义 |
| 8 | 与主流开发环境的**集**成 | IDE内嵌版本控制功能 |

## 二、测试管理工具

### 2.1 自动化测试工具

软件自动化测试包含4个阶段：

::: tip 核心口诀
**「划设施执」**
:::

| 阶段 | 内容 |
|:---:|------|
| **计**划 | 确定自动化测试范围、策略、资源 |
| **设**计 | 设计测试用例、选择测试框架 |
| **实**施 | 编写测试脚本、搭建测试环境 |
| **执**行 | 运行测试、收集结果、分析报告 |

**两大代表工具**：

| 工具 | 类型 | 核心能力 |
|------|------|---------|
| **UFT** (原QTP) | 功能测试 | GUI录制回放 + API测试 + 数据驱动 + 关键字驱动 |
| **LoadRunner** | 性能测试 | 虚拟用户生成器 → Controller → Analysis 三位一体 |

### 🔥 华航实战：从手工到自动化

> 平台初期测试全靠手工，发版前回归测试需3人×3天。2024年8月，我们引入**Selenium WebDriver**（Web端）+ **JUnit**（API端）构建自动化测试框架，在Jenkins中集成为CI流水线的一个阶段。每次代码提交自动触发300+条冒烟测试用例，回归测试时间缩短至**45分钟**。LoadRunner用于性能压测，验证了平台**5000并发下响应时间<200ms**的SLA要求。

### 2.2 测试管理工具 — 7大功能

::: tip 核心口诀
**「划例执陷报协集」**
:::

| 序号 | 功能 | 说明 |
|:---:|------|------|
| 1 | 测试计**划**管理 | 定义测试目标、策略、范围 |
| 2 | 测试用**例**管理 | 用例的设计、实施、执行和维护 |
| 3 | 测试任务**执**行 | 执行用例、记录结果、管理数据 |
| 4 | 缺**陷**记录跟踪 | 记录缺陷→跟踪直至解决 |
| 5 | **报**告和分析 | 进度报告、结果报告、缺陷报告 |
| 6 | 团队**协**作 | 任务分配、进度跟踪、沟通交流 |
| 7 | **集**成其他工具 | 与需求管理、持续集成、自动化工具集成 |

**测试管理工具的核心**：

::: tip 核心口诀
**「例陷」** — 测试用例库 + 缺陷库
:::

- 围绕测试用例：用例管理、测试套件管理、测试执行结果 → 「**例套果**」
- 围绕缺陷：缺陷记录、缺陷跟踪、分析报告 → 「**录踪报**」

**三大代表工具**：

| 工具 | 定位 | 特点 |
|------|------|------|
| **TestRail** | 测试用例管理 | Web界面，支持基线分支，集成Jira/GitHub |
| **Quality Center** | 全流程测试管理 | 明确需求→测试计划→执行测试→跟踪缺陷 四阶段 |
| **Bugzilla** | 缺陷跟踪系统 | 开源、自定义字段/工作流、邮件通知、API扩展 |

## 三、研发与测试环境搭建和维护

### 3.1 环境搭建8原则

::: tip 核心口诀
**「现协似自灵隔维」** （缺"覆盖率"口诀）
:::

| 原则 | 说明 | 华航实践 |
|------|------|---------|
| 可重**现**性 | 方便复现问题并调试 | Docker镜像固化环境配置 |
| 可**协**作性 | 多人协作避免冲突 | Git分支+沙箱工作空间 |
| 与生产环境相**似** | 减少环境差异问题 | 测试环境K8s集群与生产同构 |
| **自**动化环境管理 | 减少人为出错 | Ansible自动化部署 |
| **灵**活性 | 尝试新方法、框架和工具 | 按需创建/销毁测试环境 |
| 环境**隔**离性 | 避免环境干扰 | 每人独立Docker Compose环境 |
| 可**维**护性 | 随时更新和维护 | 定期更新基础镜像 |

### 3.2 环境部署5步骤

::: tip 核心口诀
**「硬统程库测」**
:::

| 步骤 | 内容 |
|:---:|------|
| **硬** | 硬件设备的选取和配置 |
| **统** | 操作系统的安装和配置 |
| **程** | 应用程序的安装和配置 |
| **库** | 数据库的安装和配置 |
| **测** | 测试工具和脚本的准备 |

### 3.3 环境维护4要求

::: tip 核心口诀
**「备更清监」**
:::

| 要求 | 内容 |
|:---:|------|
| **备** | 定期备份研发测试环境数据 |
| **更** | 定期更新软件和补丁 |
| **清** | 定期清理数据和日志 |
| **监** | 监控研发测试环境状态 |

## 📊 易错对比总结

| 对比项 | A | B | 关键区别 |
|--------|---|----|---------|
| 版本控制架构 | SVN集中式 | Git分布式 | 离线能不能干活 |
| 监控模型 | Nagios推(Push) | Prometheus拉(Pull) | 谁发起数据采集 |
| 自动化类型 | Puppet/SaltStack批处理 | Jenkins操作自动化 | 批量配置 vs 持续集成 |
| 测试工具层次 | UFT/LoadRunner执行工具 | TestRail/QC管理工具 | 干活 vs 管活 |
