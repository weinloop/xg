# 第10章 云原生觉醒

> **教材对照**：第10章 云原生系统规划（10.1 发展背景 · 10.2 技术架构 · 10.3 建设规划 · 10.4 实践案例）

---

## 一、一次发布拖垮一个夜班

安全规划落地一个月，平台稳了，问题却换了方向。

营销在大促前要给主数据服务加一个「里程标签」字段。林小白评估：改一行字段，却要把单体主数据应用整体重新打包、停服发布。运维选在凌晨两点割接——结果证件查询、备降订阅、外站报送跟着一起停了四十分钟。老周在运控群里炸锅：「改个标签，把我备降通道也停了？」

复盘会上，张架构把一张 CNCF 全景图拍在桌上：「这是**架构债**。咱们一期为了快，把主数据、订阅、规则、目录揉成一个大应用。现在每次小改动都是全量发布、全量停机。该上**云原生**了。」

刘总问：「云原生不就是上容器吗？第 6 章不是上了 Kubernetes？」

张架构摇头：「容器只是底座。**云原生是一整套架构原则和方法**——把非业务代码尽量交给云设施，业务只管业务。林小白，你跟我做《平台云原生演进规划》，二期重构。」

---

## 二、到底什么是云原生

张架构开「概念拉齐会」，不让任何人说「微服务=云原生」这种话。

他按教材讲**定义演进**：

- 2010 年 Paul Fremantle 首次提及「cloud native」  
- Matt Stine《迁移到云原生架构》：**12 要素、微服务、自服务、基于 API 协作、抗脆弱性**  
- 2015 年 **CNCF** 成立  
- Pivotal 概括四大特征：**DevOps、持续交付、微服务、容器**  

**CNCF 2018 官方定义**三点写上白板：

1. 基于**容器、服务网格、微服务、不可变基础设施、声明式 API** 构建可弹性扩展应用  
2. 基于自动化构建**高容错、易管理、可观察**的松耦合系统  
3. 构建统一开源生态，能与云厂商服务**解耦**  

林小白对照平台现状自查 **12 要素**，挑出三条踩坑的：

- **配置**：里程开关写死在代码里（违反「配置与代码分离」）——所以改字段要重新打包  
- **易处理**：单体进程启动慢，无法快速优雅停止  
- **开发与线上等价**：测试环境与生产差异大，割接才暴雷  

「先解决这三条，」张架构说，「就解决了大半夜班悲剧。」

陈工补一句区分：「**DevOps** 是开发+运营+质量保障的交集；加上安全，叫 **DevSecOps**——赵安全的等保门禁就嵌在这里，别把安全留到最后。」

---

## 三、把大应用拆成「服务」

二期重构第一步，按教材 **10.3 建设规划五步**第一项——**微服务与容器云平台**。

林小白用 **DDD（领域驱动设计）** + 主数据驱动，沿第 8 章主题域划界：

| 微服务 | 边界 |
|--------|------|
| 旅客主数据服务 | 旅客/证件/会员主题 |
| 航班状态订阅服务 | AOC 订阅与分发 |
| 数据质量规则服务 | 备降规则包 |
| 数据目录服务 | 元数据与检索 |
| 外站报送服务 | 事件上报 |

张架构提醒别拆过头：教材里**服务化架构**分**微服务**与**小服务（Mini Service）**——「旅客与会员共享大量数据，拆成两个微服务会产生大量跨服务事务，做成**小服务**共享一库更合适。大型应用别迷信『越小越好』。」

老周最关心的隔离实现了：里程标签属于「会员」边界，改它只发布会员相关服务，**备降订阅服务不停**。

---

## 四、服务多了之后：治理与 Mesh

拆完服务，新麻烦冒头：服务间调用满天飞，一个超时引发雪崩。这正是 **10.3 第二步——服务管理与治理**。

林小白搭起治理底座：**服务注册发现、配置中心、路由、负载均衡**，对外统一 **API 网关**。他特意区分两类 API：

- **微服务 API** — 内部服务间，粗粒度（延续第 5 章 SOA）  
- **OpenAPI** — 对外（局方、机场、营销合作方），强认证、限流、审计  

张架构引入 **Mesh 化架构**：「把熔断、重试、mTLS 这些中间件能力从业务进程剥离，下沉到 **Sidecar**，业务只留薄 Client。」林小白这才明白教材那句「中间件从业务进程分离」——他不用再在每个服务里写一遍重试逻辑。

可观测性补齐 **10.2.3 可观测架构**三件套：

- **Logging** — 日志入对象存储  
- **Tracing** — 全链路追踪，备降一次调用串起六个服务  
- **Metrics** — 网关 QPS、服务时延上大屏  

老周点名要 Tracing：「下次再延迟，我要看到卡在哪个服务，别再甩锅中间件。」

## 五、流水线即城墙：持续交付与安全

**10.3 第三步——持续交付及安全**，把第 9 章的安全规划真正焊进流程。

林小白搭 **DevSecOps** 流水线，闭环为：**持续集成 → 持续部署 → 持续交付 → 监控 → 反馈**。

| 阶段 | 嵌入的安全/质量门禁 |
|------|----------------------|
| 提交 | 代码扫描、密钥泄露检测 |
| 构建 | 容器镜像漏洞扫描（第 9 章接入） |
| 部署 | 等保基线校验、配置合规 |
| 运行 | RBAC 鉴权、API 网关认证 |
| 反馈 | 备降场景自动化回归 |

「认证和权限是**基础安全措施**，」赵安全强调，「不是流水线选配。IDOR 那种越权，门禁里就该拦下。」

「配置」从代码里抽出来放进配置中心——里程开关变成一条配置项，营销自助改、灰度发布，再不用半夜停服。林小白用**声明式 API + GitOps**：改动提交 Git，集群自动收敛到目标状态；**不可变基础设施**——不再登机器手改，重建而非修补。

## 六、零信任：墙搬到身份上

到了 **10.2.2 设计原则**，张架构重点讲**零信任**——「从**网络中心化**走向**身份中心化**。以前进了内网就信任，现在每次调用都要验身份。」

这正好接续第 9 章赵安全那句话。平台落地：

- 服务间 **mTLS** 双向证书，Sidecar 自动签发  
- 每次 API 调用校验身份+权限+设备状态，不因「在内网」放行  
- 外站终端即使在专线内，也要双因素+设备绑定  

七条设计原则林小白逐条对平台打钩：

1. **服务化** — 微/小服务已拆  
2. **弹性** — 大促容器自动扩容  
3. **可观测** — 三件套上线  
4. **韧性** — 目标提升 **MTBF**，熔断降级  
5. **所有过程自动化** — IaC / GitOps / Operator  
6. **零信任** — 身份中心化  
7. **架构持续演进** — 不追求一步到位  

---

## 七、韧性压测：主动找故障

**10.3 第五步——增强生产环境韧性和安全性**。张架构提出搞**混沌工程**，林小白第一次听说「主动把生产搞坏」。

演练日，工程师用 **Chaos Monkey** 随机杀掉一个旅客主数据服务实例：

- Kubernetes 探针检测失败，30 秒拉起新副本  
- Mesh 自动把流量切到健康实例  
- 备降订阅**不受影响**，老周屏上零告警  

又模拟一次区域故障，验证存算分离与异地副本——这用到 **10.2.3 存储计算分离** 与**分布式事务**：会员积分扣减用 **SAGA** 补偿，证件写入走强一致，避免 XA 性能拖累。

事件驱动改造也落地：航班状态变更作为 **EDA 事件**（带 Schema）发布，订阅方各取所需，用 **CQRS** 把查询与写入分离——这下营销画像查询再忙，也压不垮主库写入。

刘总看着监控：「故意杀进程还能不停服？」张架构答：「这就是**韧性**。MTBF 上去了，半夜割接的时代过去了。」

## 八、规划成文：顶层规划，分步实施

林小白统稿《平台云原生演进规划》，遵教材**「顶层规划 + 分步实施」**，五步骤为骨架，并附**实践案例**对标——像那家快递公司：云原生数据库（OLTP+OLAP）、应用容器化、微服务改造，换来成本（按量付费、免运维）、稳定性（5 个 9）、效率（分钟级 CI）、业务赋能。

架构层次表照搬到航空场景：

| 层次 | 星河平台落点 |
|------|--------------|
| 基础设施 | 裸金属 + 私有云 |
| 流量接入 | 云 DNS / Ingress / API 网关 |
| 平台层 | Kubernetes 云原生 PaaS |
| 应用服务层 | Namespace 隔离五大服务 |
| 运维管理 | 托管容器 + 可观测 + 混沌 |

二期收尾，营销大促当天加了三个标签字段，全程**未停服、未惊动运控**。何站长外站报送服务单独升级，总部其余服务无感。

陈工问林小白：「云原生觉醒，醒的是什么？」

林小白说：「以前我觉得云原生是新潮技术。现在懂了——它是让**业务代码只管业务**，把弹性、韧性、安全、可观测交给平台和云。我那段半夜停服的痛，本质是**非业务的事缠住了业务**。」

陈工合上电脑：「方法篇到此为止——规划、应用、云、网、数据、安全、云原生七章。下一篇是**能力篇**，从**治理**开始。技术能落地，靠的是治理、服务、人、流程、研发、资源、项目这些**管理能力**。下周李姐和数据委要重组治理架构，你跟着。」

林小白合上笔记本，第一次没有追问「那我还写代码吗」。

## 【林小白的考点笔记本】

### 10.1 发展背景
定义演进（Fremantle / Stine / CNCF2015 / Pivotal 四特征）；CNCF 2018 三点定义；12 要素；DevOps / DevSecOps。

### 10.2 技术架构
- 架构定义：非业务代码交云设施；代码三部分（仅业务核心）。  
- **设计原则七条**：服务化、弹性、可观测、韧性（MTBF）、过程自动化、零信任（身份中心化）、持续演进。  
- **架构模式七种**：服务化、Mesh、Serverless、存算分离、分布式事务、可观测、事件驱动。  
- 可观测三件套：Logging / Tracing / Metrics。分布式事务：XA / 消息最终一致 / TCC / SAGA / AT。  
- 优势六条。

### 10.3 建设规划五步
微服务+容器 → 服务治理 → 持续交付与安全 → 自服务基础设施 → 韧性安全（混沌工程）。

### 10.4 案例
快递公司：云原生库+容器化+微服务；五层架构；四类效益。

## 【陈工的应试锦囊】

**案例题**

| 题干 | 答法 |
|------|------|
| 改小功能要全量停服 | 微服务拆分；配置分离；声明式 API |
| 服务雪崩/超时 | 服务治理；Mesh 熔断；可观测 |
| 安全留到最后 | DevSecOps；门禁前置；零信任 |
| 系统经常宕 | 韧性；混沌工程；MTBF |
| 高并发查询压垮库 | 存算分离；CQRS；EDA |
| 跨服务一致性 | SAGA/TCC，避免 XA |

**论文**：单体到微服务演进；DevSecOps 流水线；零信任身份中心化；混沌工程提升 MTBF。

**选择陷阱**：设计原则七条；架构模式七种；Serverless 适用/不适用场景；可观测三件套；分布式事务模式；零信任=身份中心化。
