# 第05章 应用怎么长出来

> **教材对照**：第5章 应用系统规划（5.1 基础知识 · 5.2 主要内容 · 5.3 主要过程 · 5.4 常用方法 · 5.5 软件工厂）

---

## 一、三家厂商，三种「中台」

招投标前夜，信息中心会议室灯火通明。三份标书摊在桌上，封面清一色「企业级数据中台」。

**甲司**：「一站式大数据平台，三天上线数据湖。」  
**乙司**：「微服务中台 + 低代码，业务人员自助建模。」  
**丙司**：「航空行业套件，旅客、航班、运行模块开箱即用。」

刘总看向林小白：「规划是你写的。明天述标，你问。问不出真问题的，厂商随便吹。」

林小白心里发虚——他写过 Spring Boot，没主持过述标。陈工递来一张检查单，标题是**应用系统规划**五类产出物：

| 规划内容 | 明天要问的话 |
|----------|----------------|
| **生命周期** | 一期旅客主题，你们瀑布还是迭代？ |
| **体系结构** | 与运控实时域怎么解耦？ |
| **接口** | 外部局方报送、内部 CRM，接口谁定义？ |
| **数据** | 概念模型谁建？物理库放哪？ |
| **构件** | 主数据服务是独立构件还是嵌在 ETL 里？ |

「应用不是规划文件的附录，」陈工说，「是规划长出来的**血肉**。血肉长歪了，骨架再漂亮也站不住。」

## 二、述标日：用 APA 拆穿组合

述标会，林小白先不讲技术，让三家填同一张**应用系统组合**清单——教材 **APA 法**第一步：

| 应用域 | 现有系统 | 一期目标 | 建设方式 |
|--------|----------|----------|----------|
| 旅客主数据 | CRM | 统一 ID | ？ |
| 航班状态 | AOC | 订阅服务 | ？ |
| 外站报送 | Excel/传真 | 在线事件 | ？ |
| 数据目录 | 无 | 登记与检索 | ？ |
| 质量规则 | 无 | 备降场景规则 | ？ |

甲司填「全部新建数据湖，旧系统割接」——张架构摇头：「运控 AOC **稳态**，割接等于炸机房。」

乙司填「全部微服务重写」——周数据冷笑：「CRM 才用三年，**重写**不是规划，是赌博。」

丙司填「套件+接口适配，旅客域新建、运控只读订阅」——与规划里**平台能力主线、稳态先行**最接近。

林小白按 APA 后续步骤在心里走了一遍：**评估 → 分析组合 → 优化策略 → 实施计划 → 监测评估**。他在白板写下结论：

> 一期组合策略：**新建旅客主数据与治理构件，集成现有 CRM/AOC，外站报送轻量 SaaS 化模块，数据目录与质量引擎平台化。** 拒绝「大湖一刀切」和「全量微服务重写」。

刘总当场让丙司牵头、甲司提供大数据组件、乙司提供 API 网关——**组合优化**，不是「赢家通吃」。

## 三、可行性：算得清账才能招标

中标组合敲定后，李姐拉财务、运控、法务做**可行性研究**。

教材四方面：**经济、技术、社会、管理**——林小白负责写报告初稿，陈工要求走全 **8 步**：

1. 复查目标规模（一期三任务，旅客 95%、备降 95%、外站 100%）  
2. 研究现行系统（二十余套，重点 CRM/AOC/离港）  
3. 导出新系统高层逻辑模型（DFD 0 层：源系统→平台→消费系统）  
4. 重新定义问题（不是缺中台，是缺主数据与质量闭环）  
5. 评价方案（甲单建、乙重写、丙组合）  
6. 推荐丙主导组合方案  
7. 草拟开发计划（12 个月，三期里程碑）  
8. 提交审查  

**经济可行性**吵得最凶。财务总监要三年 ROI：

- **总成本**：建设 2800 万 + 年运维 420 万（含外站网络改造）  
- **总效益**：直接——减少重复录入人力 180 万/年、报送罚款规避 50 万/年；间接——备降处置缩短、旅客投诉下降、为营销精准化奠基  

林小白算不出精确 NPV，但做出**敏感性分析**：若旅客 ID 覆盖率不到 80%，营销效益为零——「**基本可行**，但依赖治理执行。」

**技术可行性**：张架构签字——混合云、API 网关、主数据引擎成熟；运控只读订阅可行；外站 VPN 升级已立项。

**社会可行性**：工会问会不会裁人。答复：减少重复录入，人员转岗数据质量与客服分析——**管理可行**前提。

结论：**可行**，附条件——运控接口须签 SLA，外站网络改造与平台同步。

## 四、客服中心里的详细调研

可行性过关，项目组进入**详细调研**——工作量比外站大巴那次大十倍。

林小白跟周数据在客服中心泡了五天，按教材 **9 方面范围**逐项填表，守 **6 原则**：自顶向下展开、用户参与、看改进可能、工程化、全面与重点结合、主动友善。

重点捞到的鱼：

**数据和数据流**：客服查旅客需跳转四个系统，平均 6 分钟。  
**业务流程**：备降改签 11 步，3 步系统外。  
**决策过程**：是否给金卡旅客安排酒店，靠值班长经验，无结构化规则。  
**现存问题**：特殊旅客信息在纸质单，**改进意见**：与旅客主数据一并建模。

调研 **6 项活动**全用上：发调研表（200 份）、开调研会（运控营销机务三场）、访问（老周夜班）、现场跟单（跟 CA2847 模拟演练）、**原型**（把 89% 匹配原型搬到客服桌面）、与管理部门复查建议。

林小白学会**需求优先级**：P0 旅客 ID、备降状态同步；P1 特殊旅客、外站报送；P2 标签画像。

老周看完原型：「这玩意要是上周就有，我少打二十个电话。」——**用户参与**不是签字画押，是让人愿意说真话。

## 五、系统分析：做什么，先钉死

详细调研完，进入**系统分析**——回答「**做什么**」，不是「怎么做」。

陈工把团队关进培训室两天，方法写在墙上：

**问题分析 → 需求分析 → 需求定义**

需求引导用三种：**原型法**（已有备降匹配）、**JAD 联合会议**（运控营销同室吵完签字）、**观摩法**（客服跟单录像）。

分析手法林小白选 **UML 用例** + **DFD** 双轨：

- 用例图：旅客「备降改签通知」、外站「不正常事件报送」、数据管理员「质量规则配置」  
- DFD：CRM/AOC/离港为外部实体，平台为加工，旅客主数据存储为数据存储  

**功能性需求**摘录三条：

1. 系统应提供集团级旅客唯一标识，并映射各源系统键值。  
2. 系统应在航班状态变更后 60 秒内推送至订阅方（运控域可配置为边缘直推）。  
3. 系统应支持备降场景数据质量规则包的一键启用与熔断。

**非功能性需求**：可用性 99.9%、运控接口只读、旅客敏感字段脱敏、外站弱网降级缓存。

《系统说明书》陈工逐条审：**正确、完整、一致、无二义、可修改、可跟踪**——第六条「可跟踪」要求每条需求有编号，对应 CSF 与测试用例。林小白以前写用户故事从不编号，这次吃到亏：改一条需求，十页文档联动修改。

## 六、系统设计：怎么做，分两层

分析签字后，张架构带队做**系统设计**——**总体设计（概要）** + **详细设计**。

### 概要：架构与生命周期

一期生命周期选 **增量建设**迭代：先旅客主数据+订阅，再质量规则+外站报送，再目录与报表——不是瀑布一次交付，也不是无边界敏捷。

架构上，张架构画 **四层**：

```
界面交互层 — 目录门户、质量工作台、外站报送 Web
业务处理层 — 主数据服务、订阅路由、规则引擎
数据处理层 — 采集、清洗、匹配、审计
数据存储层 — 主数据库存、日志湖、配置库
```

符合 **以数据为中心** 的平台特征；消费端 B/S，运控侧 **API+消息队列** 近似三层 C/S 演进。

**关注点分离**：界面不管匹配逻辑；规则引擎不直连 CRM 库——**模块化 + 低耦合**。林小白想起 **9 个基本概念**：抽象（业务/过程/数据/技术四层抽象）、模式（主数据用**工厂**创建不同源适配器）、**信息隐蔽**（规则脚本对客服不可见）、**功能独立**（内聚高、耦合低）、**求精**自顶向下、必要时**重构**旧 ESB 适配层。

### 详细：接口、数据、构件

**接口定义**三要素：

| 类型 | 一期内容 |
|------|----------|
| **用户界面** | 置用户于控制之下（可取消批量操作）；减记忆负担（统一旅客检索）；保持一致（跟集团 OA 风格） |
| **外部接口** | 局方事件报送 API、机场联合运行数据交换（预留） |
| **内部接口** | CRM 双向同步、AOC 只读订阅、财务票款回写 |

界面四问也进设计：响应时间≤3 秒、在线帮助、出错提示带工单号、命令式批量用向导。

**数据定义**走数据库五步法：

需求分析 → **概念模型**（ER：旅客、证件、联系、会员、特殊服务）→ **逻辑模型**（3NF 主表+映射表）→ **物理模型**（主库 Oracle 集群、日志 MongoDB）→ **验证**（用 CA2847 脱敏数据跑通）。

**构件定义**：标识域类「旅客」「状态变更事件」；基础设施类「适配器」「订阅通道」；细化持久化与行为；部署图标注外站边缘缓存构件。

概要阶段用**变换型数据流**设计：输入 CRM/AOC → 清洗匹配 → 输出主数据/订阅。质量规则包用**事务型**入口：选场景「备降」→ 激活规则集。

## 七、TOGAF 与 SOA：把 ADM 跑一轮

丙司架构师老吴进场，提议用 **TOGAF ADM** 管一期工程。林小白第一次见十阶段全文：

**预备 → 需求管理 → 架构愿景 → 业务架构 → 信息系统架构（应用+数据）→ 技术架构 → 机会与解决方案 → 迁移规划 → 实施治理 → 架构变更治理**

老吴说：「咱们不是每个阶段都做全套文档。一期跑 **需求管理→架构愿景→业务架构→IS架构→技术架构→迁移规划→实施治理**，其余持续迭代。」

林小白对照项目填：

- **架构愿景**：旅客数据单一可信源，支撑 CSF 四条  
- **业务架构**：备降处置 BPMN，砍掉 3 个系统外手工步  
- **应用架构**：主数据服务、订阅服务、规则服务、目录服务四个 **SOA** 粗粒度服务  
- **数据架构**：旅客主题 ER + 映射，与第 8 章数据规划衔接  
- **技术架构**：混合云、API 网关、Kafka、主数据引擎  
- **迁移规划**：CRM 先映射、AOC 后订阅；外站最后一批  

**SOA 原则**写在接口规范首页：明确接口、自包含模块化、**粗粒度**（别为每个字段建服务）、**松耦合**、互操作与策略声明。服务注册进集团 API 网关，**服务治理**含版本、熔断、审计。

运控老周质问：「服务多了会不会更慢？」

老吴答：「粗粒度订阅，一次推整条航班状态对象，不是拆成一百个细服务。」

## 八、软件工厂与交付之争

开发模式上，丙司提出建设**软件工厂**——林小白以为是厂房，陈工解释：**兰德公司 1955 年概念**，把人、机、工具、流程、质量五条流水线化。

| 软件工厂要素 | 星河一期落地 |
|--------------|----------------|
| 专业人员 | 专班+厂商联合团队，数据旗手驻场 |
| 基础设施 | 混合云 Dev/Test/Prod 三环境 |
| 工具技术 | Git、CI/CD、自动化测试、元数据血缘工具 |
| 流程规范 | TOGAF 治理 + 敏捷两周迭代 |
| 质量管理 | 需求跟踪矩阵 + 备降场景自动化回归 |

与传统开发对比：**敏捷交付**（两周迭代）、**流水线**（提交即构建）、**安全可靠**（等保要求进流水线门禁）、**协同开发**（运控、客服参与评审）。

乙司代表不服：「工厂会不会变僵化？」

陈工答：「工厂不是瀑布。敏态模块——外站报送 UI——用**敏捷**；稳态模块——主数据引擎——用**V 模型**左侧设计、右侧测试，单元/集成/系统/验收四层对应需求到代码追溯。」

林小白在《应用系统规划说明书》里写下**生命周期组合策略**：

- 旅客主数据核心：**增量迭代**（演化建设思路）  
- 运控订阅接口：**V 模型**严格测试  
- 外站报送：**敏捷**快速试错  
- 整体里程碑：**瀑布式门禁**（可行性→分析→设计→实施签字）

## 九、何站长看得见的东西

三个月后，外站何站长收到一台新终端——不是丙司宣传的数据湖大屏，而是**外站报送 Web** 和**旅客特殊服务录入**两个小应用，背后走同一旅客主数据服务。

何站长试录一名轮椅旅客，总部客服中心三分钟就能查到——以前传真要半小时。

林小白没写多少行代码，但他写的《应用系统规划说明书》里，每一条都能追溯到：

- **初步调研**（外站大巴）  
- **可行性**（四方面八步骤）  
- **详细调研**（客服中心五天）  
- **系统分析**（用例+DFD+需求编号）  
- **系统设计**（概要四层+详细接口数据构件）  
- **APA**（组合策略）  
- **TOGAF**（ADM 裁剪）  
- **SOA**（四个粗粒度服务）  
- **软件工厂**（联合交付）

刘总视察外站，问何站长：「好用吗？」

何站长：「我只要填一次，你们别再让我 Excel 报三遍。」

回程大巴上，陈工问林小白：「应用怎么长出来的？」

林小白说：「不是厂商 PPT 里长出来，是从调研里的痛点，经过可行性、分析、设计，一层层**求精**长出来。下一层该规划云和资源了——张架构说机房快满了。」

陈工笑：「对。别只会写 Spring Boot，先写清楚**应用要几条命**——生命周期、架构、接口、数据、构件，五条命齐了，代码才有地方落地。」

## 【林小白的考点笔记本】

### 5.2 主要内容（五类产出）

| 内容 | 本章落点 |
|------|----------|
| 生命周期 | 增量迭代+V模型+敏捷组合 |
| 体系结构 | 四层以数据为中心；变换/事务型 DFD |
| 接口 | 三类接口；UI 三原则四问题 |
| 数据 | ER 五步法 |
| 构件 | 主数据/适配器/订阅/规则 |

生命周期：瀑布/V/迭代/敏捷四价值。

### 5.3 主要过程（顺序）
初步调研→可行性→详细调研→系统分析→系统设计。

| 步骤 | 要点 | 落点 |
|------|------|------|
