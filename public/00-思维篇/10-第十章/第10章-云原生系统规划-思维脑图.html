10.1.2 发展概述 P1
  • 烟囱模式：各应用独立构建，资源难共享，大量占用且难以共享 传统IT
  • 瀑布式流程：开发/运营/质量保障分离，信息不对称，周期长 传统开发
  • 敏捷开发：解决开发效率和版本更新速度，但未打通运维
  • DevOps：开发+技术运营+质量保障三者交集，促进沟通协作，缩短周期 开发运维一体化
  • DevSecOps：DevOps + 安全，在软件生命周期每个阶段为安全负责，安全是全员责任 开发安全运营一体化 高频
🔑 易混区分：DevOps=开发+运营+质量｜DevSecOps=DevOps+安全（每个阶段都要安全负责）。口诀：「敏Dev DevOps DevSecOps全」。

10.2 云原生技术架构 架构定义七大原则七大模式六大优势 ▼
10.2.1 架构定义 已考 P1
  • 定义：基于云原生技术的一组架构原则和设计模式集合，将非业务代码最大化剥离，让云设施接管弹性/韧性/安全/可观测性/灰度等非功能特性
  • 技术依赖：传统云计算三层 — IaaS / PaaS / SaaS
  • 代码三部分：①业务代码（核心，真正带来价值）②三方软件（业务库+基础库）③处理非功能特性的代码 已考 业三非
架构带来的三大变化 P1 代非高
变化核心内容
1.代码结构巨大变化存储变成服务（对象/块/文件存储），开发人员不再需要处理高可用/扩缩容/安全/运维升级等问题，降低开发复杂度
2.非功能性特性大量委托高可用等能力委托给云计算（虚拟机热迁移/容器健康检查/Kubernetes自愈）；有状态部分交给云服务，应用变成无状态 核心思想
3.高度自动化的软件交付容器标准打包屏蔽环境差异；"面向终态"的交付方式，自动化完成安装/配置/运行/变更
🔑 易混区分：非功能性特性=高可用/容灾/安全/可运维等（无直接业务价值）｜功能性特性=建立客户资料/处理订单/支付等（直接业务价值）。口诀：「功直非间」— 功能性直接带来价值，非功能性间接支撑。
10.2.2 设计原则（七大） P0必背 服弹可韧自零架
原则核心内容关键词/场景
服务化服务化架构拆分不同生命周期的业务单元，实现独立迭代；面向接口编程，增加复用；基于服务流量的策略控制微服务/小服务；代码规模超出小团队合作范围时拆分；限流降级熔断隔仓灰度均基于服务流量
弹性部署规模随业务量自动调整，无需事先容量规划；好的弹性缩短采购到上线时间，支持业务爆发式扩张自动伸缩；无需固定硬件资源；降本+支持突发流量 核心
可观测主动通过日志/链路跟踪/度量等手段，让一次点击产生的多次服务调用耗时/返回值/参数清晰可见Logging+Tracing+Metrics；SLO度量→优化SLA；回答"服务为什么离线"等问题
韧性软件所依赖软硬件组件出现异常时的抵御能力；核心目标提升MTBF（平均无故障时间）异步化/重试限流降级熔断反压/主从/集群/AZ高可用/单元化/跨Region容灾/异地多活
所有过程自动化通过IaC/GitOps/OAM/Kubernetes Operator等标准化+自动化软件交付过程配置数据自描述；面向终态交付；CI/CD流水线实践
零信任默认不信任网络内部和外部任何人/设备/系统；基于认证和授权重构访问控制；从"网络中心化"走向"身份中心化"身份是核心问题；IP/主机/地理位置/网络均不能作为可信凭证 核心
架构持续演进架构不是封闭式，需具备持续演进能力；新建应用易选策略，存量应用迁移需考虑迁出/迁入成本/风险演进式架构；微服务/应用网关/服务网格/数据迁移/在线灰度等细粒度控制
🔑 口诀：「服弹可韧自零架」— 服务化/弹性/可观测/韧性/自动化/零信任/持续演进。口诀每个字对应一个原则。
🔑 易混区分：韧性 vs 弹性 → 前=抵御异常（MTBF），后=自动伸缩（成本+爆发）｜可观测 vs 监控 → 前=主动下钻分析，后=被动告警。
10.2.3 架构模式（七大） P0必背 服Mesh无存分可事
1. 服务化架构模式 标准架构
  • 以应用模块为颗粒度划分，以接口契约（IDL）定义业务关系，以标准协议（HTTP/gRPC）确保互联互通
  • 结合DDD/TDD/容器化部署提升代码质量和迭代速度
  • 微服务 vs 小服务：小服务=一组关系非常密切的服务的组合，共享数据，适用于超大型系统，避免接口颗粒度过细 易混
  • 优点：部署分离/单独扩缩容/单独升级；缺点：维护模块增多，缺乏自动化能力反而降低效率
2. Mesh化架构模式 中间件剥离 中业分离
  • 把中间件框架（RPC/缓存/异步消息等）从业务进程中分离，SDK与业务代码解耦
  • 业务进程只保留很薄的Client，流量控制/安全等逻辑由Mesh进程完成
  • 大量分布式架构模式（熔断/限流/降级/重试/反压/隔仓）都由Mesh进程完成
  • 南北流量 vs 东西流量：API网关=南北（外部↔内部）；Service Mesh=东西（服务↔服务）易混
3. Serverless模式 P0必背 有状长IO
  • 定义：将"部署"动作从运维中"收走"，开发者不用关心运行地点/操作系统/网络配置/CPU性能
  • 适用场景：事件驱动的数据计算任务/计算时间短的请求响应应用/没有复杂相互调用的长周期任务
  • 不适用场景（三场景）：①有状态应用（Serverless调度不帮做状态同步）· ②长时间后台运行的密集型计算任务（无法发挥优势）· ③涉及频繁外部I/O（网络/存储/服务间调用，I/O负担重、时延大）P0
  • Serverless数据库特征：计算与存储分离/一写多读架构/依据流量自动部署计算节点/对象存储/丰富RESTful API
🔑 口诀：「有状长IO，Serverless不友好」— 三个不适用场景取首字。
4. 存储计算分离模式 无状易弹
  • CAP困难主要针对有状态应用；无状态应用不存在C（一致性）维度，可获得很好的A（可用性）和P（分区容错性）
  • 推荐把各类暂态数据（session）/结构化和非结构化持久数据都采用云服务保存，实现存储计算分离
  • 例外：交易会话数据太大需不断根据上下文重新获取，可用"时间日志+快照"实现快速增量恢复
5. 分布式事务模式 P0必背 XA消TCCSAGAAT
模式特点优缺点
XA传统强一致很强的一致性，但性能差 易混
消息最终一致基于消息队列很高性能，但通用性有限
TCCTry-Confirm-Cancel应用层控制事务，隔离性可控，高效；但对业务侵入性非常强，设计开发维护成本高 有Try阶段
SAGA补偿事务模式与TCC优缺点类似，但没有Try阶段，每个正向事务对应一个补偿事务，开发维护成本高 无Try
SEATA AT开源项目模式性能非常高，无代码开发工作量，可自动执行回滚；存在使用场景限制 高频
🔑 口诀：「XA性差消息快，TCC侵SAGA同，AT无码性能高」— 五模式对比口诀。
6. 可观测架构模式 LogTraMet
  • Logging：多级别详细信息跟踪（verbose/debug/warning/error/fatal），由应用开发者主动提供
  • Tracing：提供请求从前端到后端的完整调用链路跟踪，对分布式场景尤其有用
  • Metrics：对系统量化的多维度度量
  • 需选择合适开源框架（OpenTracing/OpenTelemetry），规范上下文可观测数据，利用spanid/traceid做分布式链路分析
  • 主要目标：对SLO（服务等级目标）进行度量，从而优化SLA（服务级别协议）
7. 事件驱动架构（EDA）P1 韧CQ数开事响
  • 本质：应用/组件间的集成架构模式；事件具有Schema可校验有效性；具备QoS保障
  • 六大应用场景：①增强服务韧性（异步集成，下游失败不影响上游）②CQRS（命令查询责任分离）③数据变化通知④构建开放式接口（事件提供者不关心订阅者）⑤事件流处理（如Kafka日志处理）⑥基于事件触发的响应（IoT传感器场景）
10.2.4 架构优势（六大） P1 高灵安成自
优势核心内容
高可扩展性微服务可独立部署和扩展，根据业务需求快速增减服务实例
高可用性微服务分布在多个节点，实现负载均衡和容错处理，减少单点故障风险
灵活性微服务可独立部署管理，可使用不同编程语言和技术栈

成本效益提高可靠性/可扩展性/安全性，同时减少运维成本和时间，带来更高ROI
高度自动化与基础设施深度整合，计算/存储/网络资源管理和自动化部署交给PaaS，应用更灵活

规划原则与方法 顶分五步
  • 核心思路：云原生内容做不到一步到位，需"顶层规划+分步实施"，边建设边交付价值，确保可持续性
  • 五步路线图：基于技术之间关系和实践经验定义，每步可分若干子项目，可能需要多次迭代
⚡ 五步实施路线图 P0必背 案例高频 微服持续自增
步骤名称核心工作
第一步微服务采用及运行环境容器云平台构建基于容器+Kubernetes构建私有容器云平台；以云原生12要素为指导设计微服务；DDD/主数据驱动设计方法；容器云平台提供弹性扩展/服务路由/健康检查/错误隔离/资源调度等自服务能力
第二步服务管理和治理完善服务管理和治理能力；Kubernetes能力（注册发现/配置/路由/负载均衡/弹性扩容）；CNCF推荐Service Mesh代理东西流量；API网关（南北流量）两层服务治理能力；OpenAPI跨平台跨组织生态

第四步自服务敏捷响应基础设施基础设施三部分：①基础设施资源（多云管理平台封装异构资源）②支撑平台（持续交付平台/容器云平台等）③纯技术工具（消息/监控/权限/AI服务等）；构建统一身份认证/日志/配置/监控/告警/安全/消息/调度等基础服务的自服务能力
第五步增强生产环境韧性和安全性通过抗脆弱性试验（混沌工程/Chaos Monkey）持续增强环境韧性；安全能力建设是防御性的，需持续改进；Netflix的Simian Army项目"混沌猴"随机注入故障找弱点 混沌工程
🔑 口诀：「微服持续自增」— 五步首字口诀。第一步微服务+容器云，第二步服务治理，第三步持续交付，第四步自服务基础设施，第五步增强韧性。
🔑 易混区分：混沌工程 vs 安全测试 → 前=主动注入故障找弱点（如Chaos Monkey），后=防御性漏洞扫描。两者目的不同。

方法核心思想优缺点

领域驱动设计		基于业务领域划分微服务边界难清晰定义领域边界；领域划分不合理导致数据重复；缺乏全局认识；需多次迭代 主流但有问题

DevOps体系与持续交付 集部交监反
  • DevOps核心：协作反馈，及时反馈才能反思和改进
  • 持续交付闭环：持续集成(CI) → 持续部署(CD) → 持续交付(CD) → 持续监控(CM) → 持续反馈(CF)
  • 实施难点：组织架构优化（领导理解+愿意改进）；工具链打通（认证权限管理复杂）；建议自研或合作研发避免集成问题
  • 安全措施：认证和权限是基础；代码安全检查/镜像安全检查/系统安全/应用安全/接口安全/容器安全
抗脆弱性与混沌工程 混沌猴找弱点
  • 抗脆弱性：通过主动注入故障找到弱点并强制修复，从而提升环境健壮性和韧性（类比：人体免疫系统受病毒侵害后变得更强）
  • Netflix Simian Army："混沌猴"(Chaos Monkey)随机注入故障，识别并消除体系结构中的弱点
  • 实施时机：完成前几步之后，或伴随前述步骤过程，通过抗脆弱性试验持续增强韧性
10.4 云原生实践案例 快递公司Kubernetes四大效益 ▼
案例背景 千万订单TB数据
  • 公司：某快递公司（日订单千万级/物流轨迹亿级/数据TB级/1300+计算节点）
  • 原有问题：基于VMware+Oracle的传统架构；JOE架构（原文如此）；系统不规范/稳定性差/研发效率低；软件交付周期过长；大促保障难以实现；系统稳定性难以保障
  • 解决方案：采用云原生技术和架构实现核心业务搬迁上云
解决方案（三大关键点） P1
方案内容
引入云原生数据库引入OLTP+OLAP型数据库，在线数据与离线分析逻辑拆分到两种数据库，改变此前完全依赖Oracle的情况
应用容器化解决环境不一致问题，确保开发/测试/生产环境一致性；效率与速度双重提升；更适合微服务场景

上云架构（四层） 基流平应
  • 基础设施层：全部计算资源取自云服务商裸金属服务器（比ECS更优性能+更合理资源利用率+按需取量）
  • 流量接入层：云DNS+PrivateZone；两套流量接入（公网+内部调用）；Kubernetes Ingress统一域名转发
  • 平台层：基于Kubernetes的云原生PaaS平台（打通DevOps闭环/资源隔离/流量精细化管理/集成日志链路Metrics/统一APIServer支持多云混合云）
  • 应用服务层：每个应用创建单独Namespace实现资源隔离；YAML模板快速版本升级和回滚
  • 运维管理层：云服务商托管版容器服务（免运维Master节点）；自动完成扩容；降低直接操作Kubernetes集群风险

效益具体内容

稳定性云产品至少5个9(99.999%)的SLA确保系统稳定；数据异地备份；归档存储高可靠/低成本/安全性
效率一站式研发运维；持续集成流程耗时可缩短至分钟级；SLS日志控制台快速检索异常日志，免去登录机器查日志
赋能业务云服务商提供超过300种云上组件（计算/AI/大数据/IoT等）；开箱即用，有效节省业务创新技术成本
