# 📇 卡片15：面向服务的架构（SOA）

---

## 📖 教材原文

> 面向服务的架构（SOA）是一种软件架构设计的模型和方法论。从广义上来看，SOA是指一种新的组织应用架构和组织IT基础架构，它可以使组织实现跨应用、跨部门、跨组织甚至跨行业之间的离散系统互连。而狭义的SOA是指一种软件架构，它可以根据需求，通过网络对松散耦合的粗粒度应用组件进行分布式部署、组合和使用。

简单地说，面向服务的体系架构是一个组件模型，它将应用程序的不同功能单元通过这些服务之间定义良好的接口和契约联系起来。接口采用中立方式定义，独立于实现服务的硬件平台、操作系统和编程语言。SOA的远景目标为：让IT变得更有弹性，以更快地响应业务组织的需求。

### SOA的6个设计原则

| 原则 | 说明 |
|------|------|
| **明确的接口定义** | 接口需满足稳定、明确、封装性等要求 |
| **自包含与模块化** | 服务功能实体完全独立自主，独立部署、版本控制、自我管理和恢复 |
| **粗粒度** | 服务数量不应太多，依靠消息交互而不是远程过程调用 |
| **松耦合** | 减少各服务间的相互依赖和影响；服务的位置、实现技术、当前状态及私有数据对请求者不可见 |
| **互操作性、兼容性和策略声明** | 确保不同服务之间的互操作和兼容 |

### SOA的6个主要技术内容

| 技术 | 说明 |
|------|------|
| **服务封装** | 将业务功能封装成标准化服务，具有明确定义的接口，可被重用和独立部署升级 |
| **服务编排** | 将多个服务组合成复杂业务流，通过定义服务的依赖关系和调用顺序实现复杂业务逻辑 |
| **服务注册与发现** | 服务信息存储到注册中心，通过查询注册中心找到所需服务的地址、接口等信息 |
| **服务治理** | 服务的生命周期管理、质量保障、服务间协同，包括注册、授权、监控、日志、告警 |
| **服务安全** | 保障服务的可用性、机密性和完整性，包括身份认证、访问控制、数据加密 |
| **服务可靠性和可用性** | 通过合理设计和部署提高服务稳定性和可靠性 |

### SOA的5个主要应用场景

- **组织级应用集成**：将不同技术平台和编程语言的系统封装为服务，通过统一接口和数据交换格式实现无缝集成
- **业务流程管理**：将业务过程抽象为服务，实现业务流程的可配置、可编排和可监控
- **系统扩展和重用**：新增功能通过创建新服务来扩展，不需要修改已有服务
- **云计算和微服务架构**：将应用程序组织为云服务，通过服务治理和自动化部署来管理调度。微服务架构是基于SOA的架构风格
- **跨平台集成**：作为中间层封装和转换不同平台上的功能和数据，实现系统之间的互操作

> SOA的一个中心思想就是使组织应用摆脱面向技术的解决方案的束缚，轻松应对组织中的商业服务变化和发展的需要。通过将注意力放在服务上，使应用程序能够集中起来提供更加丰富、目的性更强的商业流程。

## 🏢 案例应用

**【华航集团项目场景】**

**问题**：华航集团120套业务系统涉及多种技术平台（Java/.NET/PHP）和数据库（Oracle/SQL Server/MySQL），异构系统间的数据共享和功能调用困难。

**考题形式**：

> 华航集团数据资产智能管理平台需要与120套异构业务系统对接，实现跨系统的数据资产统一管理和服务共享。请运用SOA的理念和方法，为该平台设计面向服务的架构方案。

**参考答案要点**：

**（1）SOA架构设计**：

```
┌─────────────────────────────────────────────┐
│              统一数据服务门户                  │
├─────────────────────────────────────────────┤
│              API网关（Kong）                   │
├──────┬──────┬──────┬──────┬─────────────────┤
│资产  │质量  │数据  │安全  │  第三方服务       │
│目录  │监控  │服务  │管控  │  （认证/消息等）   │
│服务  │服务  │服务  │服务  │                  │
├──────┴──────┴──────┴──────┴─────────────────┤
│          企业服务总线（Kafka/RabbitMQ）       │
├──────┬──────┬──────┬──────┬─────────────────┤
│数据  │数据  │数据  │数据  │  ...120套系统    │
│采集  │清洗  │转换  │加载  │  适配器          │
│服务  │服务  │服务  │服务  │                  │
└──────┴──────┴──────┴──────┴─────────────────┘
```

**（2）6个设计原则的贯彻**：
- **明确接口**：所有服务通过统一的OpenAPI 3.0规范定义RESTful接口
- **自包含**：27个微服务各自独立打包为Docker镜像，独立部署至K8s
- **粗粒度**：按业务域划分服务（资产管理、质量监控等），不按数据表粒度拆分
- **松耦合**：服务间通过API网关（Kong）间接通信，不直接依赖；数据采集服务故障不影响质量检核服务
- **互操作**：统一采用JSON数据交换格式，HTTP/HTTPS协议

**（3）6个技术内容的应用**：

| 技术 | 华航项目对应方案 |
|------|----------------|
| 服务封装 | 为120套业务系统各封装一个数据接入适配器服务（IDataConnector），标准化接口 |
| 服务编排 | 数据资产入库流程编排：采集服务→清洗服务→编目服务→质量检核服务→服务发布（Apache Camel编排） |
| 服务注册发现 | 采用Nacos作为服务注册中心，27个微服务启动时自动注册，API网关动态发现 |
| 服务治理 | Sentinel实现熔断降级（超过阈值自动降级）+ Prometheus监控 + ELK日志聚合 |
| 服务安全 | OAuth2.0 + JWT令牌认证，API网关统一鉴权，敏感数据AES-256加密传输 |
| 服务可靠可用 | 核心服务3副本部署，故障自动切换；Hystrix熔断器防止级联故障 |

**（4）5个应用场景的匹配**：
- **组织级应用集成**：核心场景——120套异构系统通过标准化适配器服务实现数据统一接入
- **业务流程管理**：资产审批发布流程（申请→审核→脱敏→发布→通知）编排为可配置的服务链
- **系统扩展和重用**：新增业务系统只需开发新的适配器服务，不影响已有120个适配器
- **云计算和微服务**：27个微服务部署在K8s集群，实现弹性伸缩和自动化运维
- **跨平台集成**：SOA中间层屏蔽各系统技术差异（Java的FOC、.NET的PSS、PHP的旧版OA等）
