# 📇 卡片07：构件定义

---

## 📖 教材原文

> 对应用系统构件进行定义，将需求模型和架构模型中的信息转化为构件表示，这种表示提供了用来指导构件（编码和测试）活动的充分信息。

### 构件定义的典型任务

**（1）标识所有与问题域对应的类**
使用需求模型和架构模型，每个分析类和体系结构构件都要细化。

**（2）确定所有与基础设施域对应的类**
在分析模型中并没有描述这些类，在体系结构设计中也经常忽略，但此时必须对它们进行描述。包括GUI（通用用户界面）构件（通常为可复用系统构件）、操作系统构件，以及对象和数据管理构件等。

**（3）细化所有不需要作为可复用构件的类**
详细描述实现类需要的所有接口、属性和操作。在实现这个任务时，必须考虑采用设计的启发式规则（如构件的内聚和耦合）。

**（4）说明持久数据源并确定管理数据源所需要的类**
数据库和文件通常都凌驾于单独的构件定义描述之上。在多数情况下，这些持久数据存储最初都作为体系结构定义的一部分进行说明。但随着细化定义过程的不断深入，需要提供关于持久数据源的结构和组织的额外细节。

**（5）开发并细化类或构件的行为表示**
UML状态图被用作需求模型的一部分，表示系统的外部可观察行为和更多的分析类个体的局部行为。在构件级设计过程中，有时必须对设计类的行为进行建模。

**（6）细化部署图以提供额外的实现细节**
部署图用作体系结构定义的一部分。在构件级定义过程中，应该对部署图进行细化，以表示主要构件包的位置。某些情况下部署图被细化成实例形式，这意味着要对指定的硬件和使用的操作系统环境加以说明，而构件包在这个环境中的位置等也需要确定。

**（7）考虑每个构件级定义表示，并且时刻考虑其他可选方案**
定义是一个迭代过程。创建的第一个构件级模型总没有迭代N次之后得到的模型那么全面、一致或精确，在进行定义时重构是十分必要的。

---

## 🔑 背诵提炼

| 序号 | 典型任务 | 核心内容 |
|------|---------|---------|
| 1 | 标识问题域类 | 细化分析类和体系结构构件 |
| 2 | 确定基础设施域类 | GUI构件、操作系统构件、数据管理构件 |
| 3 | 细化非可复用构件类 | 接口+属性+操作，遵循内聚耦合规则 |
| 4 | 说明持久数据源 | 数据库/文件的结构和组织细节 |
| 5 | 开发行为表示 | UML状态图建模设计类行为 |
| 6 | 细化部署图 | 构件包位置、硬件、操作系统说明 |
| 7 | 考虑可选方案 | 迭代过程，重构必要 |

---

## 🧠 背诵口诀

```
构件定义七任务（问基细持行部选），

问——标识问题域类全，
基——确定基础设施类（GUI/OS/数据管理），
细——细化非复用构件（接口属性操作），
持——说明持久数据源（库文件结构），
行——开发行为用状态（UML状态图），
部——细化部署定位图（硬件OS构件包），
选——迭代重构可选案。
```

## 🏢 案例应用

**【华航集团项目场景】**

**问题**：华航集团数据资产智能管理平台需要将系统架构模型中的各子系统转化为可编码实现的构件。

**考题形式**：

> 在"华航集团数据资产智能管理平台"详细设计阶段，需要对系统构件进行定义。请结合构件定义的7项典型任务，说明该平台的构件定义过程。

**参考答案要点**：

（1）**标识问题域类**：从需求模型出发，标识核心问题域类——
- 数据资产类（Asset）：资产ID、名称、分类、所属系统、数据量
- 质量规则类（QualityRule）：规则ID、规则类型、阈值、执行周期
- 数据服务类（DataService）：服务ID、接口类型、SLA等级、调用限额
- 安全策略类（SecurityPolicy）：策略ID、权限级别、加密算法

（2）**确定基础设施域类**：
- GUI构件：基于Ant Design Pro的React组件库，封装统一的数据门户页面模板
- 操作系统构件：容器化部署（Kubernetes），统一使用Linux环境
- 数据管理构件：Hudi数据湖连接器、ClickHouse JDBC驱动、Redis客户端封装

（3）**细化非可复用构件类**：
- 数据采集适配器：为120套业务系统设计统一的数据接入接口（I Data Connector），定义connect()、extract()、transform()方法，遵循高内聚（每个适配器只负责一个系统）低耦合（通过标准接口解耦）
- 质量检核引擎：定义check()、report()方法，加载5000+条规则并执行批量校验

（4）**说明持久数据源**：
- MySQL：资产目录元数据表（asset_metadata），含id、name、category、source_system等字段
- ClickHouse：质量监控结果表（quality_check_result），按天分区
- Hudi：原始数据湖表（raw_data_lake），按业务域分目录存储

（5）**开发行为表示**：
- 使用UML状态图描述数据采集构件的状态流转：空闲→连接中→采集中→校验中→完成/失败→重试
- 描述质量规则执行的行为：加载规则→执行校验→记录结果→触发告警（若超阈值）

（6）**细化部署图**：
- 集团总部：部署平台核心服务（资产目录、质量引擎、API网关）于K8s集群（10节点）
- 5大区域中心：各部署数据采集代理和本地缓存节点
- 23家分公司：浏览器访问，无需本地部署

（7）**迭代重构**：
- 第1版构件模型交付后，发现数据采集适配器的耦合度过高（各系统适配器存在大量重复代码），通过重构抽取公共抽象基类AbstractConnector，将通用逻辑（连接管理、重试机制、日志记录）上提，降低重复代码率约40%。

| 任务 | 华航项目对应 | 关键产出 |
|------|------------|---------|
| 问题域类 | Asset/QualityRule/DataService | 4个核心实体类 |
| 基础设施类 | React GUI + K8s + 数据连接器 | 3类基础设施构件 |
| 细化非复用构件 | IDataConnector接口 | 统一数据接入规范 |
| 持久数据源 | MySQL/ClickHouse/Hudi | 3类存储方案 |
| 行为表示 | 采集/校验状态图 | UML状态图 |
| 部署图细化 | 总部K8s+区域代理+浏览器 | 三层部署架构 |
| 迭代重构 | AbstractConnector基类抽取 | 重复代码减少40% |
